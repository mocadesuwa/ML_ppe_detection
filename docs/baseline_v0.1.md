# 实验室防护用品佩戴检测：Baseline 方案 v0.1

编写日期：2026-10-07

状态：可评估的方案草案，首版程序框架已实现。本机 GPU 已检查，原始数据已下载，初步标注检查发现 11 份问题，尚未生成划分或训练。用户要求一步一步进行且暂不训练，当前停在框架检查节点。课程要求待补充，训练参数仍为建议值。

阅读导航：[数据集选择](data_selection.md)、[本机环境检查](environment_check.md)、[实验记录模板](experiment_record.md)。

## 1. Baseline 是什么

Baseline（基线）是项目的第一个完整实验方案：采用明确的任务、固定的数据划分和一组初始训练设置，获得可记录、可复现的结果，作为以后改进的比较起点。

本项目的 baseline 应完成“图片与标注 → 数据检查 → 微调预训练模型 → 验证 → 保存模型 → 预测示例 → 分析错误”这条完整流程。

只让已有 YOLO 在一张图片上画出框，可以验证软件是否可用；要成为本项目的 baseline，还需要使用本任务的数据训练并评价。

## 2. 第一版任务定义

项目总目标：实验室防护用品佩戴检测。

第一版子任务：对图片中可见、佩戴状态能够明确判断的人脸进行目标检测。根据候选数据集的标签，建议保留正确佩戴、未佩戴、错误佩戴三类，下载抽查后定稿。

| 类别编号 | 类别名称 | 含义 | 标注范围 |
| --- | --- | --- | --- |
| 0 | mask | 人脸上佩戴口罩，覆盖口鼻 | 人脸区域 |
| 1 | no_mask | 人脸未佩戴口罩 | 人脸区域 |
| 2 | mask_incorrect | 有佩戴口罩，但未正确覆盖口鼻 | 人脸区域 |

三类采用一致的人脸框规则，具体边界以经检查后采用的数据集标注规范为准。如果已有数据集框的是口罩本体，不能直接改名当成人脸状态数据。

相比初稿的两类设计，增加第三类是为了保留候选数据的原始含义。仍然只检测一种用品，任务规模比较明确。若最终选用的数据没有可靠的错误佩戴标注，则恢复二分类，并记录可评价的任务范围。

输入：一张图片，可以包含多人。

输出：每个被检测人脸的矩形框、类别、置信度。例如，“左侧人脸：mask，置信度 0.87”。这里的数字仅演示输出格式。

第一版处理规则：

- 拿在手里的口罩，不属于戴口罩的人脸。
- 露鼻、戴在下巴等情况，按经过核查的数据标注规范归入 mask_incorrect，不能只凭类别名称假定所有边界情况都有一致标签。
- 含严重遮挡、状态无法判定的人脸的图片，先不纳入本次训练、验证与定量测试，并记录排除原因。若恢复二分类，含错误佩戴人脸的图片也需一致处理。这是在限定第一版数据范围，不代表模型已经能处理这些情况。
- 对纳入的数据，每张图中符合标注范围的人脸都应标注，避免遗漏目标。
- 未检测到人脸，不能据此判断某个人未戴口罩。

本版输出的是局部可见的口罩佩戴状态。它不完成个人身份识别、跨帧跟踪、手套检测或整个人的安全合规判断。

选择这个范围的原因：先用一种用品完成完整实验，减少类别规则和数据处理的复杂度。之后可以扩展护目镜或手套。如果课程要求同时检测多种用品，本版作为第一个子任务，最终交付范围需要扩大。

## 3. 数据准备

### 3.1 数据集选择条件

选择带人脸 bounding box 和佩戴状态标签的公开数据集，检查：

1. 能否下载原始图片与标注。
2. 框标的是人脸还是口罩，标签定义是否一致。
3. 是否实际包含三种状态，各类有多少目标，少数类是否足以支持评价。
4. 是否有重复图片、错误标签、漏标、模糊或无法判断的目标。
5. 错误佩戴类别的实际标注是否可靠，是否需要调整任务。
6. 来源、版本、许可和课程使用条件是否明确。

当前使用的待核查原始数据为 Kaggle 的 Face Mask Detection，来源与核查限制见[数据集选择记录](data_selection.md)。本地已确认 853 张图片与 853 份 XML，初步严格检查发现 11 份问题标注；目标数、视觉标注质量与最终划分尚未定稿。

数据规模先服从质量与可获得性。若需要自行收集，约 500–1000 张可作为工作量规划的起点，不作为效果保证或硬性门槛；已有较完整的数据集可以直接使用其合适规模。除了图片数，还要统计每类框的数量。

如果主要使用普通场景的口罩数据，应在报告中写明它与实验室场景的差异。另准备未参与训练或调参的实验室图片做补充检查；有完整标注时才能计算该部分的检测指标。

### 3.2 数据划分

- 优先检查并沿用公开数据集可靠的原始划分。
- 需要自行划分时，建议按组分成 train / val / test，比例约 70% / 20% / 10%，并记录划分随机种子 42。
- 分组依据可以是原始视频、拍摄批次、场景或同一组连拍图片。来自同一组的近重复图片不能跨集合。
- 分组之后尽量保证各集合都有三类目标；比例与类别平衡发生冲突时，先保证数据独立性。若某类在验证集或测试集没有目标，明确说明该类不能在该集合中得到有效评价，并调整划分或补充数据。
- 在划分完成后做训练数据增强，不能先生成增强图片再随机分组。

train 用来学习参数；val 用来选权重、设置阈值和分析训练过程；test 留到 baseline 设置确定后做最终评价。之后的改进实验继续沿用同一划分，测试结果不能反过来作为反复调参的依据。

### 3.3 YOLO 格式与检查

每个目标一行：

```text
class_id x_center y_center width height
```

坐标按图片宽、高归一化到 0–1。框中心的位置与框的宽、高都需要归一化。例如，800 像素宽的图片中，框宽 200 像素，对应的归一化宽为 0.25。格式依据：[Ultralytics 检测数据格式](https://docs.ultralytics.com/datasets/detect/)。

完成以下检查才开始训练：

- 图片可读取，文件与对应标签一致。
- 类别编号正确，框的宽、高大于 0，框边界不越界。
- 缺失标签逐个核实，不能一律当成没有目标的图片。
- 抽查每个集合的可视化标注，覆盖不同类别、小人脸、侧脸和多人图片。建议至少检查 30 张；不足 30 张的集合全部检查。
- 保存各集合的图片数、各类目标数、来源信息和划分清单。

## 4. 模型与初始训练设置

使用 Ultralytics YOLO11n 的预训练检测权重 `yolo11n.pt` 进行微调。它属于体量较小的 YOLO11 检测模型，官方提供训练、验证和预测接口：[YOLO11 官方说明](https://docs.ultralytics.com/models/yolo11/)。

这些预训练权重来自通用目标检测任务，需要用本项目的数据学习自定义类别；不能假定直接加载后就能输出这三类佩戴状态。

| 项目 | 初始建议 | 如何理解 |
| --- | --- | --- |
| 模型 | YOLO11n 预训练检测模型 | 从已有视觉特征开始学习 |
| 输入尺寸 imgsz | 640 | 输入尺寸基准值，具体缩放由框架处理 |
| 正式 baseline epochs | 50 | 最多训练 50 轮，每轮遍历训练集 |
| batch | 8；显存不足时降为 4，再不足降为 2 | 每一步同时处理的图片数，保存实际值 |
| 训练 seed | 42 | 固定随机种子并记录 |
| workers | 首次在 Windows 上设为 0 | 先确保数据加载流程可靠，之后可测速度 |
| early stopping patience | 15 | 验证表现持续未改善时提前结束 |
| 优化器、学习率、增强 | 使用所安装版本的默认设置 | 保存实际解析后的参数 |
| 模型选择 | 使用验证集选择 best.pt | 不用测试集选权重 |

上述数字是本方案建议，不是官方效果承诺。相关参数定义见：[Ultralytics 训练说明](https://docs.ultralytics.com/modes/train/)。

在正式 baseline 前，先用少量数据训练 1–3 轮，检查路径、标注、类别和模型保存是否正常。这次短跑只检查流程，不据此评价最终效果。

本机检测到 NVIDIA GeForce RTX 3060 Laptop GPU，显存 6144 MiB，驱动版本 616.92。当前默认 Python 为 3.14.0，其 PyTorch 为 2.12.1+cpu，CUDA 可用性检查返回 False，且未发现 Ultralytics 包。因此硬件具备尝试本地小模型训练的条件，软件训练环境尚未就绪。详见[环境检查记录](environment_check.md)。

正式实施时先建立项目独立环境，安装匹配的 CUDA 版 PyTorch 与 Ultralytics，并确认 PyTorch 能识别 GPU。CPU 可以用于小规模流程检查，不能以此宣称 GPU 环境已搭好；训练耗时仍需实际测量。

记录 Python、Ultralytics、PyTorch、GPU 和驱动版本，保存完整训练参数。固定种子有助于复现，但不同硬件和库版本仍可能造成数值差异。

## 5. 评价与推理

### 5.1 定量评价

baseline 设置确定后，用 best.pt 在独立测试集上评价，报告总体和每个类别的指标：

| 指标 | 关注的问题 |
| --- | --- |
| Precision | 报出的结果有多少正确，误报是否多 |
| Recall | 应找到的目标找到了多少，漏检是否多 |
| mAP50 | 在 IoU 阈值为 0.50 时的检测综合表现 |
| mAP50–95 | 综合更严格的多个定位标准的表现 |

这些是检测指标，类别与位置都影响结果；不能只报告一个分类 accuracy。框架的验证模式可提供相应指标：[Ultralytics 验证说明](https://docs.ultralytics.com/modes/val/)。

记录评价参数与指标计算方式。mAP 根据不同置信度下的表现计算，不应只统计展示阈值以上的少量框再充当 mAP。展示图片可暂用 confidence = 0.25，后续如需修改，只根据验证集选择并记录。

第一版不提前规定必须达到某个 mAP：数据难度、标注质量和测试场景尚未确定。先获得可信的结果，再判断改进方向。

### 5.2 可视化与错误分析

建议保存约 10 张预测示例，包含成功案例和有代表性的失败案例；先在验证集分析，最终报告再补充测试集示例。

重点检查：

- 漏检：小人脸、遮挡、模糊等情况下是否找不到目标。
- 类别混淆：正确佩戴、未佩戴与错误佩戴是否分错，尤其关注样本少的类别。
- 定位错误：框偏移、过大或过小。
- 误报：背景中没有符合要求的人脸却报出目标。
- 场景差异：换到实验室图片后是否明显变差。

每类错误选一两个案例，写明现象与可能原因。可能原因是分析假设，需要后续实验验证，不能直接当成已证明的结论。

## 7. 接下来按这个顺序做

1. 补充课程是否限制 YOLO 版本、是否要求多种用品及提交日期。本机 GPU 已检查，仍需完成软件环境。
2. 筛选口罩数据集，先看真实图片与标注样例，再决定是否采用；据此定稿类别与框的规则。
3. 整理数据，检查分布、重复和标注，固定划分。
4. 建立项目目录与环境，编写数据检查、训练、评价和预测入口。
5. 完成 1–3 轮流程检查，再运行 baseline_01。
6. 记录指标和错误案例，形成 baseline 小结。
7. 根据错误选择一个改进变量，例如输入尺寸或模型规模。在同一数据划分上与 baseline 比较。

当前下一步是获取候选原始数据并抽查标注，同时准备项目独立训练环境。课程要求暂按“允许用预训练 YOLO、先做一个用品子任务”处理；若老师有其他要求，再调整任务范围。

## 8. 什么时候算第一版完成

- 类别含义与标注规则一致，数据检查已完成。
- 数据集划分固定，已检查明显的数据泄漏。
- 完成真实训练，并保存有效模型权重与运行记录。
- 独立测试集有实际评价结果，指标中没有占位数字。
- 新图片能输出框、类别与置信度。
- 能结合图片解释几种代表性错误，并说明实验室场景验证的范围。
- 根据保存的版本、配置和数据清单，能够再次运行实验。

达到这些条件，才有一个可以用于后续对比的 baseline。性能是否足以满足课程最终要求，需要结合实测结果与课程要求再判断。

## 9. Baseline 之后怎么改进

先根据验证集错误确定方向，每次主要改变一个因素。可考虑以下实验，但无需全部进行：

| 实验 | 与 baseline 的主要差异 | 要验证的问题 |
| --- | --- | --- |
| exp_01 | 输入尺寸从 640 改为 800；若显存要求改变 batch，明确记录 | 小人脸漏检是否改善，时间与显存代价多大 |
| exp_02 | YOLO11n 换成 YOLO11s；其余尽量一致 | 增加模型容量是否改善类别混淆 |
| exp_03 | 按统一规则修正标注或补充少数类训练数据 | 错误佩戴类别是否改善 |

前两个实验使用同一数据版本、划分和评价规则。第三个实验明确记录数据版本变化；仅调整训练数据，保留冻结的验证集与测试集，必要的评价标注修正另行记录，不能静默更改。

用验证集比较并选择最终方案，baseline 和最终方案在冻结的测试集上报告结果。单次实验的小幅差异未必可靠；如果改进很小，可用多个随机种子复跑，报告均值与波动。
